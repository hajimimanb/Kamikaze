# RL 阶段 1 计划评审报告（critic / 客观评审官）

> 评审日期：2026-08-26 ｜ 评审依据：docs/rl_stage1_arch.md、docs/rl_spec.md、docs/rl_roadmap.md + **实际代码核验**（src/model/train_rl.py、src/agent/policy.py、src/model/net.py、src/model/attn_modules.py、src/model/rl_losses.py、src/model/rl_reward.py、tools/eval_vs_sl.py）
> 结论：架构方向基本合理，但 **计划与已实现代码严重脱节**，且存在 3 个会直接毁掉训练正确性的实现级缺陷。以下按「先修正确性 → 再谈效果」排序。

---

## 0. 总评

计划书（rl_stage1_arch.md）描述的是一个**目标设计**；当前代码（train_rl.py v1）只是骨架，约 60% 的计划能力尚未实现或接线错误：

| 计划（§7） | 代码现状（核验） |
|---|---|
| 引擎全局事件 build_events_from_game（20/20） | **train_rl.py 完全不传 events** → 静默回退 build_events 座位拼接（0/20 已知缺陷） |
| 32 局池 + 3 inner epoch × minibatch 512 | 每局一次更新、整局单 batch、单步 Adam |
| 分层 lr 3e-4/3e-5/3e-4 + warmup500 + cosine | 单一 lr 3e-4，无 schedule |
| GRU Φ 差分奖励 + 终局 settlement_pt | 每轮得分差/100000（v1 奖励，Φ 未接线） |
| 对手池（随机/SL/历史 ckpt）+ 多进程 | 单进程，只有 RandomOpponent |
| 归一化混合熵 5 头 + H_target=0.35 自适应 | 仅 discard 熵、固定 0.01、**熵项是 Python float 无梯度** |
| value 用 value_pretrain.pt 覆盖 | 默认 --ckpt 直接加载 value_pretrain.pt 整网（需核实其 trunk 是否=transfer_final） |

因此工作量估算必须包含"把计划实现出来"，而非"跑起来"。

## 1. 架构评审（EventCausalAttn / 逐通道门控 / 事件 token）

### 1.1 逐通道门控：存在「梯度饥饿」硬伤（高）
- 现状：`ctx=tanh(event_attn(ev))`，`h'=h+σ(ctx_gate)⊙ctx`，ctx_gate 初始 −5 → σ≈0.0067。
- 问题 1（梯度流）：dL/d(event_attn 参数) ∝ σ(gate) ≈ 0.0067。即便分层 lr 给 10×（3e-4 vs 3e-5），旁支有效学习速度 ≈ 0.0067×10 ≈ 0.067×主干 —— **旁支比宣称的"正常学习"慢约 15 倍**。arch §10.4 的处置"gate 均值仍<0.01 → 检查 lr"找错了原因。
- 问题 2（语义）：ctx_gate 是**静态参数**（与输入无关的逐通道缩放），不是输入相关的门控——它等价于把对角缩放折进 out 投影。它能保护旧权重，但不能"按局面选择性地注入"。
- 建议：① 初始 gate 提到 −2~−3（σ≈0.12~0.05）；② 或改输入相关门控 gate=σ(Linear(ctx))；③ 或分阶段：先冻结 trunk 训旁支 N 步再联合；④ 至少把"gate 是否开启"的判定阈值改成看 gate 均值是否显著>0 且分支 loss 有梯度。

### 1.2 门控可解释性预期不成立（中）
- 计划称"gate 逐通道分化（river 组大、hand/shanten 组小）"。但 gate 有 256 个通道，对应 **trunk 潜在特征通道**，与 284 个输入通道组（river/hand/shanten）无直接对应——这个"可解释证据"在语义上不成立。可改为统计"注入前后 head 输出的差异"或对各输入通道组的敏感性分析。

### 1.3 事件 token 设计缺陷（中）
- 46 维 token 实际只承载 38 个真实事件（4×8 打牌 + 3×2 副露）+ 26 个补零。副露 token 只取 tiles[0] 的牌种：**吃牌的构成（456 vs 345）与"被叫的哪张"信息丢失**；暗杠/明杠/加杠只靠 meld_kind 区分，缺少杠后摸牌信息。
- 轮次特征 round_idx/8 对**整条序列恒为当前轮值**：64 token 跨轮时，上一轮事件被错误标成当前轮。补零在左 + 可学习位置编码使"最新事件永远处于位置 63"，模型无法感知"这是本局第 10 个事件还是第 64 个"（轮内巡目、距立直后手切数等时序信号缺失）。
- 因果注意力在 build_events 的座位拼接顺序上是**结构性错误**："只看过去"限制的是人为拼接序，不是真实时间序（即 0/20 缺陷的根源）。
- 与 284 通道的冗余：river 192 通道已编码全部打牌+手切标记，旁支的新信息主要是**全局时间序 + 时序压缩**。方向合理（主干是纯静态 Conv1d，无时间轴），但预期增益有限，需靠消融证明。

### 1.4 注入点单一（中）
- 只在 50 块之后注入一次、单一 256 维全局向量广播到 34 个牌位。所有决策头共享同一上下文，缺少"每候选牌位"或"每对手"的差异化。对阶段 1 可接受（等价 Suphx 式全局条件化），但别期待读牌级收益（那是阶段 2 ③④ 的事）。

### 1.5 合理之处（予以肯定）
- 新模块 ~0.6M 参数 vs 主干 ~20M，开销可忽略；strict=False + missing=12 方案正确；位置编码 N(0,0.02) 合理；因果掩码用 triu(-inf) 在 fp32/AMP 下无 NaN 风险；tanh 压缩 + 小门控的保护式初始化思路本身没错（只是幅度过头）。

## 2. 训练方式评审（PPO / 奖励 / 熵 / 验收）

### 2.1 【高·正确性】critic 与熵项在当前代码里**完全没有梯度**
- train_rl.py:171 `values = ...detach()` → value_loss 梯度恒为 0（critic 永不更新，GAE 用的 V(s) 永远停在预训练初值）；
- train_rl.py:177-178 `H = float(np.mean(ents))` → 熵项是常量，对 loss 无梯度，熵正则实际失效；
- 计划书描述的是正确形态，但**实现必须修**：去 detach（critic 应可训练）、熵改为张量项、并加集成测试断言 dL/d(critic)≠0、dL/d(policy)≠0、初始 ratio≈1。

### 2.2 【高·正确性】logp 分布不一致 → 初始 ratio ≠ 1（PPO 前提被破坏）
- 阈值头（ron/tsumo/kyushu）：行为=阈值判定（确定性），logp 却记成 Bernoulli 的 log σ((z1−z0)/T)（policy.py:274/278/282、train_rl.py:112-115）——**行为策略 ≠ 计 logp 的策略**，重要性比有偏；
- 声明阶段（pass/pon/chow/kan）：采样时用"温度缩放+归一化"的 ps（policy.py:295-296），_recompute_logp 却用**未归一化、未缩放的原始乘积**（train_rl.py:124-132）——同一策略下 old≠new，r_t≠1；
- 建议：RL 训练期对 3 个阈值头也做 Bernoulli 采样（阈值仅用于评估），且采样与重算共用同一 logp 函数（单一数据源），并在 smoke 里断言"未更新前 ratio≈1"。

### 2.3 【高】事件旁支在训练与验收中都用的是 0/20 缺陷事件源
- train_rl.py rollout（65 行）不传 events、ppo_update（155 行）不传 events → policy._logits 回退 build_events（座位拼接，代码注释自认"离线近似"）；
- eval_vs_sl.py 同样调 act() 不传 events → 消融"event-attn on/off"对比的不是"有无时序信息"，而是"有无（乱序）时序信息"。**必须先接线 build_events_from_game**（经 game.events）到 rollout 与验收，否则 ② 的独立贡献无法被正确测量。

### 2.4 【中】奖励设计与尺度
- 当前 v1 奖励=每轮得分差/100000，量级 ~0.001，且一局内仅 8~18 个非零奖励步（其余 400+ 步为 0）→ GAE 信号极稀疏；γ=0.99 下跨轮衰减严重（γ^50≈0.6）。
- Φ 差分奖励（计划 v2）能提供逐轮密集信号，是"正确性"级依赖，不是锦上添花；但 rl_reward.py 存在**两套不一致的终局奖励表**：TERMINAL_REWARD["tenhou_hanchan"]=(15,4,−6,−15) vs SETTLEMENT_CONFIG["tenhou"].uma=(20,10,−10,−20)。Φ 的训练目标与 RL 终局奖励必须同源，否则 Φ 在预测一个与结算不同的效用（自举偏移）。
- 奖励尺度与 value 初值尺度需核对（value_pretrain 的训练目标尺度未知）；建议加 advantage 归一化（当前无）。

### 2.5 【中】验收统计功效不足
- 25 局/座位 × 4 座位 = 100 局：se≈0.047，66% 门槛的 95% CI ≈ ±0.094，**单次评估在真实胜率 0.55~0.75 间都可能随机翻车**；
- 且"对 SL 基线"实际是 **1 打 3（A vs 3×B 镜像）**：均势玩家期望 win_rate = 0.25+0.5×0.25 = **0.375**，66% 意味着 A 需约 45% 首位率——门槛很高，需提前校准预期；
- 建议：至少 100 局/座位（400 局）、3 个种子取均值并报 CI，或把门槛改为"均值 ≥0.66 且下界 ≥0.60"。对每 500 局训练内评估可用缩减版，但**最终验收样本量不能省**。

### 2.6 【中】其余训练风险
- 无 KL/行为约束：熵自适应（H_target=0.35 高于 SL 熵？未测）可能主动推高探索，导致弃牌行为漂移；建议先测 SL 熵，H_target 取 SL 实测值。
- 分层 lr 是合理且重要的（防旧权重被毁），但若 §1.1 不修，分层反而放大饥饿；warmup/cosine 可后置。
- Φ 漂移控制（每 500 局监控 / 每 2000 局重训）设计完备，但依赖 Φ 先被训练出来（当前只有 reward_pred_smoke.pt，train_reward_pred.py 仍在 [~] 状态）——**Φ 未就绪前不要开 RL 主训练**。
- 对手池在历史 ckpt 不足时退化为"随机+SL 自镜像"，可接受；但多进程+GPU 批量推理是吞吐关键（目标 1 万局/时），当前单进程串行 GPU 调用远达不到。

## 3. 工作量估算

前提：修复 §2.1/2.2/2.3 三个正确性缺陷 + 实现计划书核心能力。按 1 名熟悉该代码库的工程师计：

| 工作项 | 人·天 |
|---|---|
| 正确性修复：critic/熵梯度、logp 统一、ratio≈1 集成测试 | 1.5–2.5 |
| 事件接线：rollout/重算/验收 传 build_events_from_game + 序列化轨迹存储 | 1–2 |
| 32 局池 + episode 边界 GAE + minibatch 512 + 3 epoch 更新循环 | 1–2 |
| Φ 全量训练（28K 局）+ 逐轮奖励接线 + 漂移监控/重训循环 | 2–3 |
| 对手池（随机/SL/历史）+ 多进程引擎 + 批量 GPU 推理（吞吐工程） | 2–4 |
| 分层 lr + warmup/cosine + 熵自适应（归一化混合熵） | 0.5–1 |
| 门控改进（初值/输入相关门控/分阶段） | 0.5–1 |
| 验收升级（样本量、多种子、CI）+ 消融脚本整理 | 0.5–1 |
| 监控面板、失败处置协议、日志 | 0.5–1 |
| **合计** | **≈ 10–17 人·天** |

GPU·小时（假设 1×GPU 训练 + CPU 引擎采样）：
- 训练：5 epoch × 2000 局 = 1 万局。若吞吐做到 3000–10000 局/时 → **3–15 GPU·时**；若维持单进程串行（现状态）→ 30–80 GPU·时（墙钟更长，瓶颈在 CPU 引擎与 IO）。
- 每 500 局自对战评估：数百局 × 2 策略 ≈ 分钟级；Φ 重训 5 次 × 500 步 ≈ 分钟级。
- 验收（400–1600 局）≈ 0.5–2 GPU·时。
- **合计 ≈ 10–40 GPU·小时**（含调试重跑余量），墙钟受采样吞吐主导；"数小时级"仅在完成批量推理工程后成立。

## 4. 优先级建议

**必须先修（否则训练无意义）**
1. 事件旁支接线（train_rl + eval_vs_sl 都传 engine events）——消融与创新 ② 的前提；
2. critic/熵梯度修复 + logp 分布统一（初始 ratio=1 断言）；
3. Φ 奖励接线（或明确降级为 v1 得分差奖励并接受其稀疏性）；
4. 验收样本量提升 + 多种子 + CI（否则 66% 门槛是掷硬币）。

**强烈保留**
- 分层 lr（trunk 3e-5 防旧权重漂移）、消融 A/B（创新 ② 的科学核心）、门控保护式初始化（但按 §1.1 调整幅度）、4 座位轮换、Φ 漂移监控（可先只监控不重训）。

**可砍/后置**
- warmup/cosine（AdamW+固定 lr 即可起步）、熵自适应（先用固定 coef，测 SL 熵后再开）、对手池 v1 只用随机+自镜像、多进程批量推理（v1 可单进程，但需接受吞吐）、③④ 模块（阶段 2 再动）、神谕引导（计划外，勿做）。
