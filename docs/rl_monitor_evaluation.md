## 2. 实时性 — 5.5/10

### 证据

**✅ 通过项**
- 面板 `<meta http-equiv="refresh" content="5">`（HTML L2）——5s 整页自动刷新机制存在。
- HTTP 可达：`curl http://127.0.0.1:8090/rl_train_panel.html` → **200，8540 bytes，8ms**（http.server 8090 服务 checkpoints 目录）。
- 评估开始时（11:16）render 循环 2 实例存活（PID 61084 / 45736：`python -u -c "from rl_train_dashboard import render; [ (render(), time.sleep(5)) for _ in iter(int,1) ]"`），面板 5s 周期更新。
- 进度行解析实测通过：`read_progress()` 对真实日志行
  `[rl] epoch 1 game 0/30 avg_p=-0.0804 avg_v=39.0444 H=0.068 ratio=1.0000 clip=0.000 353s`
  解析出 `{'epoch':1,'game':0,'games':30,'lp':-0.0804,'lv':39.0444,'H':0.068,'ratio':1.0,'clip':0.0}` —— 正则与打印格式完全匹配。

**❌ 阻断级问题（实测）**
1. **面板循环进程已死亡且无自愈**：11:18:2x 后 `rl_train_dashboard` 的 2 个 render 进程全部消失（11:20:21 wmic 复查仍无），**同时刻其他 4 个面板循环（rl_prep/rl_timeline/transfer_data/neg_pool）均存活**，唯独本面板的循环没了。面板文件停在 11:19:34，此后不再更新（数据已推进到 epoch 1 + DONE，面板却冻结）。
2. **`logs/rl_train_dash.log` 恒为空（0 字节）**：render 循环从不写任何日志/心跳，进程死亡无证据、无告警、无重启机制。该文件作为"面板循环在跑"的证据是不成立的。
3. **更新间隔实测异常**：11:16:15 → 11:18:20（间隔 **125s**）→ 11:19:34（间隔 **74s**），远非 5s 周期 —— 循环在死前已不稳定（可能双实例互踢或 render 偶发异常退出，`-c` 循环无 try/except，render 抛异常即进程退出）。
4. **进度行粒度过粗**：`train_rl.py` L296 `if gi % 200 == 0` 才打印进度 → 30 局/epoch 时**只有 game 0 打一行**，整个 epoch（~6 分钟）进度条恒显 "game 0/30"，直到 epoch 结束。实时性观感差。

## 4. 异常报出 — 8/10（机制完整，可靠性有缺陷）

### 告警清单与触发验证（伪造 metrics 实测，8 类全部触发成功）

对 `rl_train_dashboard.check_alerts` 直接注入伪造 pts + 端到端 `render()` 到临时文件验证 HTML 渲染：

| # | 告警 | 级别 | 触发条件（代码 L59-89） | 实测结果 |
|---|---|---|---|---|
| 1 | ratio 偏离 | bad 🚨 | 最后一条 `ratio∉[0.8,1.2]` | ratio=1.5 → `🚨 ratio 偏离 [0.8,1.2]: 1.5000（采样/重放 logp 不一致风险）`，红底 .alert div 渲染 ✅ |
| 2 | NaN/Inf | bad 🚨 | lp/lv/H 任一 NaN/±Inf | lp=NaN、H=Inf 均触发 `lp/H = NaN/Inf（训练数值异常）` ✅ |
| 3 | clip 率 | warn ⚠️ | `clip_rate>0.10` | 0.35 → `PPO clip 率 35.0% > 10%（更新步长过大）` ✅ |
| 4 | gate 锁死 | warn ⚠️ | `gate_mean<0.02` 且 ≥2 条 | 0.001 → `gate 均值 0.0010 < 0.02（事件旁支疑似锁死，检查分层 lr）` ✅ |
| 5 | value 尺度 | warn ⚠️ | `value_std<0.1 或 >100` | 250 → `value_std 250.00 异常（尺度失配…）` ✅ |
| 6 | wr 回退 | warn ⚠️ | `wr_vs_sl 下降 >0.05` | 0.55→0.30 → `wr_vs_sl 回退 0.550 → 0.300（策略退化信号）` ✅ |
| 7 | 进度停滞/进程死亡 | bad 🚨 | 训练日志 mtime >300s | 伪造 400s 旧 mtime → `训练日志 6 分钟无更新（进程可能死亡/卡死）` ✅ |
| 8 | 尚无 metrics | warn ⚠️ | 无 metrics 且日志缺失/过期 | → `尚无 metrics（训练未启动或未完成首个 epoch）` ✅ |

### 端到端渲染验证
伪造 2 条 metrics（含 ratio=1.5、clip=0.35、gate=0.001、value_std=250、wr 回退）→ `render()` 返回 4 条告警，HTML 生成 4 个 `⚠️ .warn` div；单独 ratio=1.5 场景生成 1 个 `🚨 .alert` div。**告警→HTML 渲染链路完整。**

### ❌ 可靠性缺陷（实测）
1. **"进程死亡"误报实测发生**：M1a 为 30 局/epoch（约 346-364s/epoch），epoch 内无进度行打印 → 静默期 >300s 阈值。评估期间实测 `check_alerts` 在训练进程正常存活（2GB 内存 python 进程在跑）时返回 `('bad','训练日志 5 分钟无更新（进程可能死亡/卡死）')`。**每个 epoch 尾部必然误报**。阈值应随 epoch 时长自适应，或训练侧增加 60s 心跳行，或检测真实 PID。
2. **面板自身进程死亡无告警**：本评估实测 rl_train_dashboard 循环死后，无任何渠道报出（日志空、无守护）。"进程死亡告警"只覆盖训练进程，不覆盖监控进程自己。
3. **告警无历史/无持续提醒**：5s 整页刷新，告警只反映当前时刻；无告警历史、无标题闪烁/声音。

- 全中文标签 + emoji 图标（🎯🔄📉🧠🚪🏆🚨⚠️✅），语义直观。

### ❌ 问题
1. **整页 meta 刷新**：每 5s 整页重载 → 滚动位置重置、页面闪烁（表格 12 行时需滚动，体验差）。
2. **无 `<meta name="viewport">`**：移动端/窄窗口查看无自适应。
3. **gate_std 显示误导**：卡片"gate 均值/std = 0.119 / 0.000"——实际 gate_std=0.00021，%.3f 四舍五入成 0.000，看起来像零方差。

5. **状态卡判定缺陷（实测）**：`running = mtime<300s` 优先于 DONE 检查 → 训练实际完成后（日志已写 `RL_V1 DONE`）面板仍显示"🔄 运行中"最长 5 分钟；且面板冻结时（循环死亡）若日志 mtime 新鲜，同样显示"运行中"。实测冻结面板显示"运行中"+ epoch 1 · 60 局完成，而训练其实已 DONE。
6. **vs-SL 标题口径错误**：图标题"每 epoch 自对战 8 局"，实际代码为 2 sweep × 4 seat × 2 game = **16 局**（train_rl.py L328-336；代码注释写"10 局"也不对）。

## 6. 不足与改进清单

### 训练者最想看、但面板没有的（按重要度排序）

1. **Φ 预测准确率 / 漂移监控（最重要）**：`docs/rl_stage1_training_plan.md` §4 明确要求"Φ 漂移: 每 500 局天凤日志 MSE 监控，>30% 恶化触发重训"，`docs/rl_stage1_arch.md` §7.5 规划了 `logs/rl_phi_monitor.json`（MSE + 相关性）。**这是计划里写了但面板完全没做的唯一监控项**——而 Φ 是整套差分奖励的地基，Φ 漂移直接决定奖励信号是否可信。
2. **奖励分布**：每轮奖励 r = Φ(x1..k) − Φ(x1..k−1)，训练者最关心奖励均值/std/分布形态，面板无任何奖励统计（metrics 也未记录）。
3. **对手池构成**：T3 两段课程（epoch 0-1 随机对手 → epoch 2+ SL 主对手，随机权重 = clip(1−wr/0.66, 0, 1)）。面板不显示当前对手是谁、混合比例多少——训练者无法判断胜率曲线的对手背景。
4. **资源占用**：GPU/CPU/内存/吞吐（局/s）。实测训练进程占 ~2GB RAM，面板零资源信息；正式 2000 局训练数小时，无资源视图无法评估吞吐工程效果。
5. **wr 置信区间**：wr_vs_sl 仅 16 局点估（0.125），无 CI；验收口径是 100 局 + 95% CI 下界 ≥0.60。面板注释"目标 0.66"无 CI 提示，早期小样本极易误读。
6. **PPO 熵目标对比**：规格 §3 有"熵正则 + 自适应系数"，面板只显示原始 H，无目标熵/系数曲线。
7. **lr 调度**：warmup 500 → cosine + 分层 lr（event_attn/ctx_gate 3e-4、trunk 3e-5、value 3e-4），无任何显示。
8. **T5 阈值再校准状态**（每 2 epoch 一次）无显示；进程 PID 显示（计划 §6 误杀防护提及 PID 记录）无显示。

## 7. 改进清单（P0 / P1 / P2）

### P0 — 阻断级，正式训练（M1b）前必须修

- **P0-1 面板循环守护**：rl_train_dashboard render 循环无守护/无日志/无自愈（本次实测已死且无痕）。需：supervisor（如重启脚本/计划任务）+ 每 5s 心跳写入 `logs/rl_train_dash.log` + 循环死亡时面板自身显示"面板进程离线"告警。
- **P0-2 进程死亡误报**：300s 阈值 vs M1a epoch 静默期 ~364s → 每 epoch 尾部必然误报 bad（已实测触发）。改法任选：阈值按 epoch 时长自适应（如 max(300, 2×epoch 期望时长)）；或训练侧每 60s 心跳行；或检测训练真实 PID 存活。
- **P0-3 进度行粒度**：`gi % 200 == 0` 对 30 局/epoch 只打 game 0。改为每 5-10 局打印或按时间（每 60s）打印；面板进度才有实时意义。
- **P0-4 状态判定修复**：`running` 判定应结合 (a) 日志含 DONE 标记 → 立即"✅ 完成"；(b) 真实进程存活；(c) mtime 新鲜度三信号，而不是 mtime<300s 一票优先。

### P1 — 训练者可操作性，M1b 期间应补

- **P1-1 Φ 漂移/MSE 监控上板**（计划 §4 已要求，接 `logs/rl_phi_monitor.json`）：Φ MSE 曲线 + 阈值告警（>30% 恶化）。
- **P1-2 奖励分布**：metrics 增加 reward_mean/reward_std（或直方图桶），面板加曲线/卡片。
- **P1-3 wr 置信区间**：wr_vs_sl 附 Wilson/normal CI（16 局下至少显示样本量），标题"8 局"改"16 局"。
- **P1-4 资源占用**：CPU/内存/局·s 吞吐卡片或曲线。
- **P1-5 对手池构成**：显示当前对手类型 + T3 随机权重（clip(1−wr/0.66,0,1)）实际值。
- **P1-6 双实例去重**：当前 venv + 系统 Python 各跑一份训练与渲染（同写 jsonl/txt/HTML，last-write-wins），应统一启动脚本并做 PID 去重（项目已有 kill_dupes.ps1，说明问题已知）。
- **P1-7 已记录字段上板**：value_mean、elapsed_s 展示；统一 elapsed_s 口径。

### P2 — 体验与锦上添花

- **P2-1** 加 viewport meta；整页刷新改局部更新（或刷新后保持滚动位置）。
- **P2-2** gate_std 精度：`%.4f` 或 <0.001 时标注"~0"。
- **P2-3** 表/卡单位统一（wr 统一为 %）。
- **P2-4** 告警历史/静默/标题闪烁提醒。
- **P2-5** lr 调度、分层 lr、熵目标/系数、explained variance、KL 等进阶曲线。
- **P2-6** T5 阈值再校准状态、训练进程 PID 显示。

## 8. 结论
